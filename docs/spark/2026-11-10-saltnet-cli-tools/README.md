# SaltNet CLI 开发脚本

这些脚本是做 `feat/saltnet-cli` 分支时用的开发辅助，不是产品代码：把任务交给别的工具、审查它们的结果、跑完整验证、提交。分工和每一步的流程写在[实现计划](../2026-11-10-saltnet-cli-plan.md)的「分工与流程」里，这里只讲脚本怎么用。分支做完之后，这个目录可以整个删掉。

需要：zsh、git、rsync、tar、node、python3；`agy`（Antigravity CLI）和 `codex`（Codex CLI）在 `PATH` 里或者在 `~/.local/bin/`。

## 约定

- **输出目录**是环境变量 `SALTNET_WORK`（默认 `$TMPDIR/saltnet-cli-work`）。在 Claude Code 会话里把它指到会话的草稿目录。
- 所有脚本都从自己所在的位置找到仓库根目录，在哪个目录下运行都可以。
- **快照**：交给别的工具的永远是仓库的一份临时副本，不是真实的工作区。它是一个没有远端的独立 git 仓库，只有一个提交 `base`，`node_modules` 从真实目录链进去，所以能跑 `tsc` 和 `vitest`。副本里**没有** `.env*`、没有真实的 `.git`、没有 `~/.saltnet`。工具改了什么，就是副本相对 `base` 的差别，以补丁的形式拿回来；协调者读完补丁，再用 `git apply` 打进真实的工作区。
- 工具脚本都不会 commit、push，也不会改真实的工作区。只有 `finish.sh`（勾计划、整理格式）和 `commit.sh`（提交）会动真实的仓库。
- 跑得久：`agy` 一次 10 到 20 分钟，`codex` 也可能这么久。用后台运行（Bash 的 `run_in_background`），结束时会收到通知，不要轮询。

## 脚本

| 脚本                                                   | 做什么                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `delegate-agy.sh <名字> <brief 文件> [模式]`           | 把一个简单任务交给 Gemini 3.8 Flash (Medium)（Antigravity 的 `agy`，模式默认 `accept-edits`）。结果在 `$WORK/delegate/<名字>/`：`response.txt`（它说了什么）、`patch.diff`、`files.txt`、`run.log`。它能用的命令有白名单（见脚本），被拒绝的命令会让整次运行中止、改动全部丢掉，所以 brief 里要写清楚它有哪些命令（见 `brief-template.md`）。`AGY_MODEL` 可以换模型。P1 里用它做了大部分模块、测试和文档，每次约 10 到 20 分钟。                                                                                                                                                                    |
| `delegate-codex.sh <名字> <brief 文件>`                | 把一个新功能交给 GPT 5.6 Sol (high)（`codex exec`）。**必须**设 `CODEX_MODEL_WRITE` 为 Codex 里 GPT 5.6 Sol 的模型 id（故意没有默认值）；`CODEX_EFFORT` 可以改推理强度。沙盒是 `workspace-write`（只能写快照，不能联网），审批关掉，需要更多权限的命令会直接失败而不是等人回答。结果同上，多一个 `events.jsonl`。                                                                                                                                                                                                                                                                                   |
| `review-codex.sh <名字> <brief 文件>`                  | 请 GPT 6.1 Sol (high) 审查真实工作区里**还没提交**的改动。审查用的快照以最后一次提交为 `base`，未提交的改动叠在上面，`git diff base` 就是被审查的改动，沙盒只读。brief 写这一步要做什么、哪里最要看，标准的审查要求由脚本接在后面（按 bug、安全、测试漏洞、仓库规则分组，每条要有 file:line 和触发条件）。**必须**设 `CODEX_MODEL_REVIEW`。`REVIEW_BUILTIN=1` 同时再并行跑一遍 Codex 自带的 `codex review --uncommitted` 当第二意见（它和自定义说明不能一起用，所以它看不到 brief），结果在 `review-builtin.txt`。结果在 `$WORK/review/<名字>/review.txt`。审查意见是线索，不是结论：逐条核实再改。 |
| `verify.sh [--build]`                                  | 整棵工作区的完整验证：`pnpm check`、`pnpm lint`、根目录所有 `test:*`、`render-service` 的测试和类型检查（`--build` 再加 `pnpm build`，动了网页端代码或 `shared/core` 时要加）。每项一行 `ok`/`FAIL`，失败的附日志末尾；日志在 `$WORK/v/`。                                                                                                                                                                                                                                                                                                                                                          |
| `finish.sh <步骤> [--build]`                           | 勾掉计划里这一步的复选框，用 Prettier 整理 `AGENTS.md` 和计划，再跑 `verify.sh`。要几分钟，在后台跑，等最后一行 `finish exit=<n>`（用法在脚本开头）。                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `commit.sh "<标题>" "<正文>" ["<验证>" ["<AI 协助>"]]` | 提交工作区里的一切，除了用户自己的 `.env*` 和 `.wrangler`。说明的格式是标题、正文、`Validation:`、`AI assistance:`；参数用单引号，里面不要有撇号。                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `mutate.py <改动.json> <测试文件>...`                  | 破坏检查：每个改动是 `{"name", "file", "old", "new"}`（`file` 相对仓库根，`old` 必须只出现一次），逐个改源码、跑指定的 `cli/` 测试、再改回来；测试失败算被发现，没失败就是漏网，最后列出漏网的。改动列表要针对这一步的代码自己写。                                                                                                                                                                                                                                                                                                                                                                  |
| `brief-template.md`                                    | 交给工具的任务说明（brief）的模板。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `coordinator-prompt.md`                                | 让新的协调会话接着往下做的启动提示。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

## 试过的和没试过的

- 2026-11-14 在一个玩具仓库里把三个交给工具的脚本各跑了一次，都正常：改动以补丁拿回来，审查在快照里发现了删掉的文件和新增的文件；`.env` 不在快照里。调用方式是拿用户 `~/.codex/config.toml` 里的默认模型（`gpt-6-luna`）试的，**没有**用过 GPT 5.6 Sol 和 GPT 6.1 Sol 的模型 id。第一次正式用之前，先确认 id 能用：`codex exec -m <id> -s read-only --ephemeral "reply ok"`。
- `codex review --uncommitted` 不能带自定义说明（试过，会报错），所以带 brief 的审查走 `codex exec -s read-only`，自带的 `codex review` 作为可选的第二意见。第二意见在试跑里指出了脚本自己的一个真问题（`SALTNET_WORK` 给相对路径时输出写错地方，已经改成先转成绝对路径），带 brief 的那一遍只指出了没写进 brief 的改动。两遍各有用，新功能和涉及凭据的步骤两遍都跑。
- Codex 的 stderr 里会有「`[features].multi_agent` 已弃用」之类来自用户自己配置的警告，无害。
- `verify.sh`、`finish.sh`、`commit.sh`、`mutate.py` 是 P1 期间用的脚本，整理时把写死的路径改成从仓库位置推出来；`delegate-agy.sh` 的白名单和快照做法没变。
