# Repository Guidelines

## Keeping This Guide Current

Treat `AGENTS.md` as living project documentation. Whenever a change adds, removes, renames, or reorganizes modules, commands, tests, deployment paths, architecture boundaries, or contribution requirements, update this guide in the same commit or pull request. Review referenced paths and commands before merging so the file remains a reliable quick index to the current codebase.

## Project Structure & Module Organization

SaltNet is a three-package pnpm workspace:

- The root package is the Vue 3/Vite PWA. `src/main.ts` bootstraps Vue, Pinia, MDUI, and the router; `src/App.vue` is the application shell.
- `src/pages/` contains route-level views. Route declarations and browser-history behavior live in `src/components/app/router.ts`.
- `src/stores/` owns global Pinia state, currently including router layout and dialog-history coordination.
- `src/components/data/` contains domain logic: `music/` for the loaded chart metadata (IndexedDB cache and Vue state around the shared SaltMeta fetch), `chart/` for score/rating UI and calculations, `kaleidxscope/` for the songs-page overview component backed by the shared `ScoreSection` (its gate data lives in `shared/core/kaleidxscope/`), `user/` for profiles, updates, backups, rating history, and the IndexedDB-backed per-chart score event history, and `collection/` for the IndexedDB cache and Vue arrays around the shared LXNS collection mapping, shared collection visuals, combined requirement/progress display, collection dialogs, reusable collection-progress evaluation, and the reactive wrapper (`relatedCollections.ts`) around the shared reverse-association index used by ChartInfo.
- `src/components/integrations/` contains external-service adapters for Diving Fish, LXNS, Nearcade, SaltNet, and asset loading. Keep service-specific API types and token logic inside the relevant folder.
  SaltNet's `postAPI` checks HTTP errors and switches to the fallback backend; `postAPIJSON`
  also parses JSON and propagates backend errors or a friendly message for invalid responses.
- `shared/core/` holds platform-neutral domain logic shared by the web app and the CLI. It must not
  depend on Vue, MDUI, localForage, `import.meta.env`, the DOM, or anything under `src/`; its own
  imports are relative, and web code imports it through the `@core/*` alias. `pnpm check` type-checks
  it with `shared/core/tsconfig.json` (no DOM or Node types) and the `saltnet/shared-core-boundary`
  block in `eslint.config.js` rejects framework imports. See `shared/core/README.md`. Current
  contents:
    - `mai/`: rank, combo and sync enums.
    - `music/`: types, SaltMeta conversion and fetching, cached-data restoration, `MusicSort` order,
      and the precomputed simplified/traditional, pinyin and romaji search index (`music/search.ts`; `createMusicSearchVariants` also reports which of the three a normalized text was reached by, and `createMusicSearchIndex` is built from it). `music/duplicates.ts` folds the banquet songs that upstream lists twice into one entry (only the CLI asks for it; the web app keeps both) and `music/fetch.ts` offers the SaltMeta download and the conversion separately as well as together.
    - `config.ts` and `http.ts`: `CoreConfig` and the injectable `FetchLike`.
    - `chart/`: difficulty, chart identity, recent-change ordering.
    - `course/`: dan-course definitions and ordered chart matching.
    - `kaleidxscope/`: CN gate conditions, life calendars, draw pools.
    - `collection/`: collection types, LXNS data mapping and validation, static characters and
      partners, version-plate requirement/progress evaluation, the music-to-collection reverse index
      builder.
    - `user/inGame.ts`: in-game user types.
    - `query/`: the songs-page query helpers in `songs.ts` (ordering, category filtering, position
      indexes, grouping and statistics as pure functions), which re-exports the web search in
      `search.ts`: existing matches ranked by exact ID, whole title/alias, name prefix, name
      substring, name pinyin/romaji, artist, charter, then score/status. Equal relevance preserves
      incoming order; transliteration is cached per metadata object and refreshed when text changes.
    - `fixtures/`: a trimmed real SaltMeta document with a helper that converts it, used as fixed
      test data by every package, plus a trimmed copy of the four LXNS collection lists (`lxns.ts`).
    - `integrations/`: `diving-fish/type.ts`, `lxns/type.ts`, and the public
      `lxns/fetchCollection.ts`.
- `src/components/rendering/` is the frontend rendering client. Reusable B50 payload, image, font, and download-filename logic lives in `shared/rendering/` and is consumed by both packages.
- `render-service/` is the Cloudflare Worker/Vercel image-rendering package. `src/worker.ts` is the Worker entry, `tests/` contains its Vitest suite, and both root and package-level `api/render/[...path].ts` files adapt the shared HTTP handler for Vercel deployments.
- `cli/` is the `saltnet` command-line tool for agents (package `saltnet-cli`, Node 24). `src/main.ts` is the entry point (it only connects `runCli` in `src/cli.ts` to the real process), `build.mjs` bundles it and the parts of `shared/core` it uses into `cli/dist/saltnet.mjs` with esbuild (git-ignored; the `bin` entry points at it), and `tests/` holds its Vitest suite (`tests/harness.ts` runs a command line in-process with captured output). It imports core through the same `@core/*` alias as the web app. `src/commands/` holds the typed command registry (`registry.ts`, the single source that argument parsing, `--help` and later `schema`/`guide` are generated from; every command also declares the JSON Schema of its `data` as `dataSchema`, put together with the builders of `src/output/schema.ts` from the shapes in `src/catalog/schemas.ts`, and `tests/commands/dataSchemas.test.ts` checks what each command prints against it with Ajv, a dev dependency of the package, so a field that is added, dropped or retyped without updating the schema fails a test), the never-throwing parser (`parse.ts`, `values.ts`), help rendering (`help.ts`), the `--limit`/`--offset`/`--fields` options every list command shares (`listOptions.ts`), the `useMetadata` helper through which a command gets the catalog current (`metadata.ts`; `useStoredMetadata` only makes the stored rows current, for `sql`), the `--with related` option of `song` and `chart` (`withRelated.ts`; the LXNS collections are fetched only when it is given) and the list of commands (`index.ts`; `search.ts` is the `search` command (default `--limit` 10), and `song.ts` and `chart.ts` are the `song` and `chart` commands (both take `--with related`); `charts.ts` is the `charts` command (filters `--level`, `--constant`, `--diff`, `--version`, `--search`, `--gate`, `--course`, `--plate`, `--collection` (the gate and the course are resolved before anything is fetched; the collections are fetched only for `--plate` and `--collection`); `--sort`, `--asc`, `--desc` and `--group-by` work too, and `--limit` and `--offset` apply to each group when grouped; the other filters, the statistics and the score orders come later); `collection.ts` holds `collection list` (every collection of every kind with `--kind` and `--search`; needs only the LXNS collections, no catalog) and `collection show` (a collection's conditions, the charts they name as chart rows with `done`, and `missing` for songs the catalog lacks); `course.ts` holds `course list` (static, no catalog needed) and `course show` (a course's life rule and its tracks as chart rows in play order, each with its `track` number, plus `missing` for tracks the catalog lacks), `kaleidxscope.ts` is the `kaleidxscope` command (the overview of all gates needs no catalog; with a gate it adds the calendar, key songs and pools, `--at` and `--diff`), `status.ts` is the `status` command (the data directory, the schema version, and for the songs and the collections when each was fetched and whether it is fresh, stale, built by another version or missing, plus the upstream songs that were merged; it never goes online and never creates the data directory), and `config.ts` holds `config list`, `config get`, `config set` and `config unset` (the settings as rows with their value, source and default; `set` and `unset` change one entry of `config.json`; all four run even when the settings have errors), and `sql.ts` is the `sql` command (one SELECT over the public views with `--limit` (default 1000, at most 10000) and `--fields`; only the sources the views it names need are made current, so a query that names no view needs no catalog and creates nothing; it runs in the sandbox described under `src/store/`)); `src/output/` turns a command's result into output: the JSON envelope (`envelope.ts`), the choice between json, tsv and text (`format.ts`, `render.ts`, `tsv.ts`, `text.ts`, `table.ts`), `--fields` projection (`fields.ts`), paging (`paging.ts`), the builders for the JSON Schemas of `data` (`schema.ts`; an object lists every key it has, so a field that is added or dropped without updating its schema fails a test) and the warning codes (`warning.ts`); `src/errors.ts` defines `CliError` and the error-code/exit-code table, `src/runtime/io.ts` wraps stdout/stderr/stdin and the network (`fetch`) so tests can inject them, `src/runtime/http.ts` gives commands a `fetch` (`ctx.http()`) that adds the User-Agent and a deadline and reports failures as `NETWORK`/`UPSTREAM_ERROR` (`tests/mockHttp.ts` answers requests from a table, and `createHarness` has no network unless a test brings one), and `src/util/` has small helpers (edit distance and nearest names, name folding, display width, command-line splitting, times with a UTC offset). Defaults for the backend, render service and LXNS client are read from the web app's `.env` files at build time (`build-defaults.mjs`). `src/runtime/` resolves the data directory (`SALTNET_HOME`, default `~/.saltnet`) and layers every setting from an environment variable, `config.json`, the build defaults and built-in defaults (`configRows.ts` shapes the settings as the rows `config list` and `config get` print; `configFile.ts` changes one entry of `config.json` for `config set` and `config unset` by rewriting the whole file in one step through `files.ts`, which `catalog/snapshots.ts` uses too, and leaves a file that is not a JSON object alone); `src/store/` is the SQLite database (`sqlite.ts` loads `node:sqlite` synchronously without its experimental warning, `store.ts` opens it in WAL mode and offers `transaction` and `read` (several queries against one consistent view), `migrations.ts` holds the numbered layout steps tracked by `PRAGMA user_version` with a backup into `cache/` first, `locks.ts` the expiring named locks, `errors.ts` maps SQLite failures to CLI errors) and is opened lazily through `ctx.store()`; `sandbox.ts` and `query.ts` are where `sql` runs (`openSandbox` copies only the public views a query names, from the database attached read-only, into a throwaway in-memory database that an authorizer limits to `SELECT` of those copies, so no base table is reachable and the real database is detached before the query is prepared; `runQuery` runs exactly one statement there and turns the rows into JSON values, reporting what SQLite objects to as `SQL_ERROR`); `src/catalog/` keeps the metadata in that database: `store.ts` replaces the songs, charts and versions built from SaltMeta and the LXNS collections (one transaction each; collection kinds are `title`, `icon`, `plate`, `frame`, plus `character` and `partner` from `static.ts`), `static.ts` writes the dan courses, characters and partners that ship with the CLI whenever their content fingerprint (`staticBuilder()`) differs from the one stored in `meta_state` (the KALEIDXSCOPE data stays out of the database), `snapshots.ts` keeps the raw downloads in `cache/`, `load.ts` reads the rows back into the structures the web app keeps (`SavedMusicList`, the mapped collections), `refresh.ts` downloads the sources under the `metadata` lock (the `saltnet refresh` command is `src/commands/refresh.ts`), and `ensure.ts` is what a command calls before it reads them: `ensureMetadata` (its first half, `ensureStored`, makes the rows current without loading them and is what `sql` calls) rebuilds rows built by another CLI version from the `cache/` snapshots, downloads what is missing or older than `metadata.maxAgeHours`, falls back to the stored rows with a `STALE_METADATA` warning, and honors `--offline` (`OFFLINE_NO_CACHE`); `songs.ts` regroups the loaded music into songs as the commands talk about them (one SaltMeta entry with its SD and DX side, `buildSongCatalog`) and indexes them by music id, chart key, title and alias (`chartKey` is the one place that writes a chart key); `search.ts` finds songs for a text (by music id, title, alias, pinyin, romaji, artist or charter), ranks the hits and reports how each was found (`matchedBy`); the song reference's last step reuses it; `chartQuery.ts` selects the charts for `charts` (every filter optional, all must pass; the order is the game's, hardest difficulty first and the newest song first within it) and `search.ts` also finds charts for `charts --search` (a song found only by a charter gives just that charter's charts); `chartSort.ts` orders charts (`--sort default|constant|version`, descending unless `--asc`; charts without a value, or of an unknown version, come last; equal charts are told apart by chart key, so the order is always the same) and `chartGroups.ts` splits them into groups for `--group-by` (the groups come in a fixed order, constants and versions from the highest and the newest, levels from the hardest, difficulties from BASIC; charts with no constant make a group whose key is null, last; `--sort` only orders the charts inside a group); `chartSets.ts` works out the charts a gate (every grade of the songs of its key condition and pools), a course (its tracks in play order), a plate or a collection (the charts its requirements name) stand for, as sets of chart keys that a query intersects (`chartQuery.ts` takes them as `within`, and `chartSort.ts` takes the play order of a course as `order`, which `--sort default` uses in place of the game's order; `listedPools` and `gateMusicIds` leave out the pool of scrambled charts, whose song no command counts as one the gate asks for); `chartRow.ts` shapes a chart as the commands print it (the shared chart row, `constantOf` (the constant a chart has; null where the game has none), and the charter, note counts and statistics only `chart` adds; unknown values are null); `courseView.ts` shapes a course (`courseInfo`) and its tracks (`courseTracks`) as the commands print them, and `gateView.ts` the gate overview, the life calendar and a gate's songs (`gateOverview`, `gatePhases`, `gateDetail`, which pick one chart per song like the web app does and put songs the catalog lacks in `pending`); `collectionView.ts` shapes a collection as `collection list` prints it (`collectionRow`; `collectionDetail` adds its conditions), picks the charts it names (`collectionChartEntries`, `collectionChartRow`) and finds the songs the catalog lacks (`missingCollectionSongs`); `relatedView.ts` works out what uses a song or a chart (`relatedTo`: the collections whose conditions name it with the charts each condition asks for, the dan courses that have it as a track and the gates that take it as a key or pool song, by the same rules as the `charts` filters); `statusView.ts` shapes what `status` says about the two downloaded sources (`sourceStatus`: when it was fetched, its age, whether it is fresh, stale, built by another version or missing, and the counts it holds) and the upstream songs that were merged (`mergedDuplicatesOf`); `views.ts` is the contract `sql` offers (`PUBLIC_VIEWS`: `v_charts`, `v_collections`, `v_collection_targets` and `v_course_tracks`, each a SELECT over the tables with its columns described and the downloaded sources it needs, so a query only makes current what it reads; `VIEWS_VERSION` rises when a query could notice a change; `viewsMentionedIn` finds the views a query names); `schemas.ts` holds the JSON Schemas of the shapes several commands print (the chart row and its collection and course variants, a song's type, what uses a song or a chart, a source's status, a setting row), written with the builders of `src/output/schema.ts` and reused by each command's `dataSchema`; `src/refs/` turns what a user typed into those entities: `difficulty.ts` (the difficulty spellings), `status.ts` (the game's spellings of ranks, combo statuses and sync statuses), `level.ts` (levels such as `13+`, and ranges where `13..14` takes `13`, `13+` and `14`), `version.ts` (a CN version by name, by name without `maimai ` or `舞萌`, by a unique part, or by its plate character), `named.ts` (the steps gates, courses, plates and collections are looked up by: a whole name, then a part of a name that only one item has; several hits are `AMBIGUOUS_REF` with at most 10 candidates, none is `NOT_FOUND` with the 5 nearest names or a fallback list), `gate.ts` (`resolveGate`: id, name or short name), `course.ts` (`resolveCourse`: id or name), `plate.ts` (`resolvePlate`: a plate or the joined label of neighbouring plates with the same requirements, such as `熊華極`) and `collection.ts` (`listCollections` of every kind, `resolveCollection`: `kind:id` or a whole name; candidates are written as `kind:id`), `setting.ts` (`resolveSetting`: a setting by its whole dotted key without regard to case or width, never by a part of a name, because `config set` writes), `song.ts` (`resolveSong`: music id, chart key, exact title, exact alias, then the search index, with `AMBIGUOUS_REF`/`NOT_FOUND` candidates) and `chart.ts` (`resolveChart`: a chart key, or a song reference plus difficulty and `--type`); `time.ts` (`parseTime`: ISO 8601 times, read in the machine's zone when written without one; `parseTimeOption` turns anything else into `USAGE`); `src/toCliError.ts` turns anything thrown into a `CliError`; `tests/setup.ts` gives each test file a throwaway `SALTNET_HOME` and `HOME`, `tests/tempHome.ts` gives each test its own fresh data directory, `tests/fixtureCatalog.ts` builds the song catalog of the fixed SaltMeta fixture, `tests/madeCatalog.ts` builds made-up songs for tests, `tests/madeChart.ts` makes one made-up chart as a catalog entry for the sort and group tests, `tests/commandRun.ts` runs one command through the harness against the mocked network (a test can add or remove environment variables), `tests/dataSchema.ts` checks a value against a published schema with Ajv in strict mode, `tests/caught.ts` returns the `CliError` a call throws, and `tests/zone.ts` (`useTimeZone`) runs a test file in a fixed time zone (the commands write times in the machine's own offset). The design is in `docs/spark/2026-11-10-saltnet-cli-design.md`.

Static assets belong in `public/`; structured source assets belong in `src/assets/`. Utility and generated-data scripts live in `script/`. Do not edit generated `dist/` files or local `.wrangler/` state.

## Architecture & Navigation Index

Start feature tracing at the route in `src/components/app/router.ts`, then follow the page into its data module or integration adapter. Production uses hash history while development uses HTML5 history; dialog navigation is coordinated between `src/stores/dialog.ts` and `src/stores/router.ts`. For B50 image issues, inspect `src/components/rendering/takumiB50.tsx`, `shared/rendering/`, then `render-service/src/http.tsx`. For music-data updates and search indexing, check `shared/core/music/saltmeta.ts`, `shared/core/music/fetch.ts`, `src/components/data/music/musicApi.ts` (the web wrapper that reports failures), `src/components/data/music/index.ts` (cache and Vue state), and `shared/core/music/search.ts`. For songs-page ordering, category filtering, position indexes, text search, grouping and statistics, inspect the pure functions in `shared/core/query/songs.ts`; `src/pages/songs.vue` only passes its reactive state to them, and `shared/core/query/songs.test.ts` snapshots their results (`pnpm test:query`). For dan-course data or its songs-page category, inspect `shared/core/course/` and `src/pages/songs.vue`. For KALEIDXSCOPE gate data or its songs-page category, inspect `shared/core/kaleidxscope/`, `src/components/data/kaleidxscope/`, and `src/pages/songs.vue`; life timestamps are stored with the CN UTC+8 offset. For collection or version-plate data, trace `shared/core/integrations/lxns/fetchCollection.ts` (via the web wrapper `src/components/integrations/lxns/fetchCollection.ts`), `shared/core/collection/map.ts`, `src/components/data/collection/index.ts` (cache and Vue state), then `src/pages/collections.vue` or `src/pages/songs.vue`. Version-plate tabs combine adjacent plates with identical score requirements into compact labels such as `熊華極` (sharing the category suffix once) through `getVersionPlateTabs` in `shared/core/collection/versionPlate.ts`, retaining the first plate as the selection value. Broader data-shape notes are documented in `docs/component-data-types.md`.

Bottom navigation spacing is derived from `env(safe-area-inset-bottom, 0px)` in `src/style.css`.
Keep overlays aligned with `--nav-bar-height` and `--nav-bar-padding-bottom` instead of adding
fixed iOS standalone offsets. `index.html` retains `viewport-fit=contain` for browser-managed
screen-edge insets.

Dialogs add same-URL browser-history entries under `history.state.__saltnetDialog`. Closed,
unmounted, or reload-stale dialog entries are skipped during `popstate`/initial reconciliation so
they cannot become empty navigation stops. Register every MDUI function dialog with
`markDialogOpen`/`markDialogClosed`; custom dialogs containing nested MDUI components must use
`.self` lifecycle listeners.

LXNS OAuth callbacks are captured and removed from the URL in `oauthSession.ts` before router
history initialization. Pending authorizations use expiring, state-keyed local storage records
and stable user UIDs; user writes are awaited through `shared.persistUsers()` before navigation
and completion. `LXNSOAuthDialog.vue` handles retries and manual callback-link transfer back to
the originating PWA when a browser uses isolated storage. Never exchange a code without its
matching local transaction and PKCE verifier. Token endpoints accept flat OAuth responses as
well as the legacy API envelope. Startup callback dialogs wait for
`dialogStore.waitForInitialHistory()` so restored dialog entries cannot close the new dialog.

## Build, Test, and Development Commands

Install all workspace dependencies with `pnpm install`. From the repository root:

- `pnpm dev` starts the frontend Vite server.
- `pnpm check` runs Vue/TypeScript checks, the DOM-free `shared/core` type check, the `cli/` type check, and verifies Prettier formatting.
- `pnpm lint` runs ESLint across the repository. Violations that predate the CLI work are frozen in
  `eslint-suppressions.json` (ESLint bulk suppressions), so only new violations fail. After fixing
  old ones, run `pnpm exec eslint . --prune-suppressions` to shrink that file; when moving a file
  that has suppressed violations, move its entry along with it. ESLint's defaults skip every
  directory named `output`, so it does not look at `cli/src/output/` or `cli/tests/output/`; run
  `pnpm exec eslint --no-ignore cli/src/output cli/tests/output` when you change them.
- `pnpm build` type-checks, builds the frontend, and generates build metadata.
- `pnpm preview` serves the production frontend build locally.
- `pnpm build:cli` bundles the CLI into `cli/dist/saltnet.mjs`; `pnpm test:cli` runs its Vitest suite.
  When developing or testing the CLI, point `SALTNET_HOME` at a temporary directory so the real
  `~/.saltnet` is never read or written.
- `pnpm --filter saltnet-render-service dev` starts the Worker with Wrangler.
- `pnpm --filter saltnet-render-service test` runs its Vitest suite.
- `pnpm --filter saltnet-render-service check` type-checks the service.
- `pnpm test:course` validates the static dan-course snapshot and ordered chart matching.
- `pnpm test:kaleidxscope` validates the gate, noise-stage, and final-sequence snapshot, life-phase boundaries, and chart matching. Unconfirmed life calendars remain empty unless explicitly requested as estimates; the noise calendar uses a labeled three-day estimate from October 1 at 07:00 UTC+8.
- `pnpm test:collection-index` runs focused tests for collection caching, initialization, the
  LXNS collection fetch and mapping, static character/partner data, the ChartInfo reverse
  association index (core builder and web wrapper), and version-plate tab merging.
- `pnpm test:score-history` validates score-change detection, IndexedDB history, generations, and
  user-backup compatibility.
- `pnpm test:recent` validates the recent charts tab ordering, score change timestamp sorting, and limits.
- `pnpm test:music-search` validates music search transliteration, script variants, and metadata indexing.
- `pnpm test:music-data` validates SaltMeta fetching (success, HTTP, version and network failures), restoration of cached music data, the duplicate-song merge, and the shared SaltMeta and LXNS test fixtures.
- `pnpm test:query` compares the songs-page query helpers (ordering, category filtering, position
  indexes, search, grouping and statistics) with committed snapshots on the fixed fixture data,
  and validates web search relevance, stable ties and compatibility with the existing match set.
  Regenerate the snapshots only for an intentional behavior change.
- `pnpm test:build-info` verifies that version timestamps ignore documentation-only and
  formatting-only commits.
- `pnpm test:oauth` validates callback cleanup, authorization recovery, user identity targeting,
  token response compatibility, refresh-token handling, serialized durable user writes, and
  initial dialog-history reconciliation.

There is no aggregate test script: before committing, run `pnpm check`, `pnpm lint`, every
`pnpm test:*` script above, and the render-service `test` and `check` commands (plus `pnpm build`
for web changes).

## Coding Style & Naming Conventions

Use TypeScript and Vue single-file components. Prettier enforces four-space indentation, double quotes, semicolons, 100-character lines, and LF endings; use `pnpm pret:fix` for formatting. ESLint uses the Antfu Vue/TypeScript configuration. Keep Vue block order as `script`, `template`, `style`; use kebab-case component names in templates. Name components in PascalCase (`ChartInfo.vue`), composables with `use...`, and variables/functions in camelCase.

## Testing Guidelines

Vitest tests live in `render-service/tests/`, alongside focused frontend data modules, and next to
the modules in `shared/core/`, using `*.test.ts` or `*.test.tsx`. Core tests may read fixed data
with Node built-ins but must not import anything from `src/`; the fixed data they share lives in
`shared/core/fixtures/`. The build metadata script has a Node test at
`script/generateBuildInfo.test.cjs`. Add focused regression cases alongside the affected service,
frontend module, core module, or script code. No coverage threshold is enforced.
Frontend changes must at minimum pass `pnpm check`, `pnpm lint`, and `pnpm build`; manually
exercise affected routes and browser back/forward behavior for UI or dialog changes. Before moving
page logic into `shared/core/`, snapshot its behavior on fixed data first (see
`shared/core/query/songs.test.ts`) so that the move can be shown to change nothing.

## Commit & Pull Request Guidelines

Follow the repository's Conventional Commit style, such as `feat: add reversed song tab setting`, `fix(render): cache full B50 fonts`, or `style(chart): refine spacing`. Keep commits narrowly scoped. Pull requests should explain behavior changes, link relevant issues, list validation commands, and include before/after screenshots for visible UI work. Review AI-generated code for readability and disclose the tool and model used, as required by the README.

## Security & Configuration

Never commit API keys, tokens, or local Wrangler state. Keep deployment-specific values in environment configuration and document any newly required variables in the relevant package.
